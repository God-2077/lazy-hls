# Lazy HLS · 按需（Just-In-Time）切片服务端实验

传统做法：先 `ffmpeg -f hls` 把整个视频切成 n 个 `.ts`，再对外提供播放列表 —— 首帧要等整个转码。
本方案：**播放列表（m3u8）是纯元数据，先算出来立刻返回**，每个 `.ts` 等客户端真的请求它时
才用 ffmpeg 现场转码（`-ss` 快速 seek，只转那几秒）并落盘缓存。

```
GET /master.m3u8              -> 瞬时（纯拼字符串）
GET /stream/720p/index.m3u8   -> ffprobe 拿时长 -> 算切片 -> 返回（<2ms）
GET /stream/720p/seg3.ts      -> 没缓存就 ffmpeg 只转这 6 秒 -> 返回并落盘
GET /stream/720p/seg3.ts      -> 命中缓存，直接读文件（几毫秒）
```

所以首帧时间只取决于**第一个切片**的转码时间，而不是整片的转码时间。

## 快速开始

> **本仓库不含示例媒体文件。** 原始的 `media/*.mp4` 体积过大（单个最大 376 MiB，
> 超出 GitHub 单文件 100 MiB 限制），已从版本库中移除并在 `.gitignore` 中忽略。
> 请自行准备样片放到 `media/` 下；档位表按源分辨率在启动时生成，任意 mp4/mkv/mov 都能跑
> （若想复现 readme 里的实测数据，需要 AV1 1080p 和 H.264 960x400 两种源）。

```bash
python server.py                          # 默认 8080，默认源 = media/ 里的 av1 1080p 那个
python server.py --source 1080            # 按关键字选 media/ 下的源（也可传完整路径）
python server.py --port 9000 --prefetch-ahead 30
python server.py --selftest               # 只检查切片方案（不起服务），CI 里也能当断言用
python tools/bench.py --cold              # 模拟播放器跑一遍，量 TTFF / 延迟 / 卡顿
python tools/check_codec.py               # 核对 master.m3u8 声明的 CODECS 与真实切片是否一致
python tools/smoke.py --port 8080         # 起服务后冒烟：播放列表 + 各档位真能转出可解码切片
```

浏览器打开 `http://127.0.0.1:8080/`：页面下方有实时指标面板，可以直接开关服务端预取、重置统计。

### 档位

档位表**按源文件分辨率在启动时生成**，不是写死的：

| 档位 | 编码 | 分辨率 | 切片 |
|---|---|---|---|
| `original` | **输出 H.264**。源本来就是 H.264 → `-c copy`（无损、零 CPU）；源是 AV1/HEVC → libx264 重编（`crf 18`，不缩分辨率） | 跟随源 | copy 时按**源真实关键帧**切（片长不均匀，实测 2.9~15.3s）；重编时固定 6s |
| `original-copy` | `-c copy`，一帧不重编，编码格式原样保留 | 跟随源 | 同上（按源关键帧） |
| `360p` `480p` `720p` `1080p` `2160p` | libx264，`-profile:v main` | 固定 | 固定 6s 一片，片首强制关键帧，可独立解码、可随机 seek |

三点说明：

* **`original-copy` 默认不进 `master.m3u8`**。AV1/HEVC 装进 MPEG-TS 大部分播放器放不出来，
  列进主列表会让整个 master 被判成「不支持」。直接访问
  `/stream/original-copy/index.m3u8` 照样能用，想对外暴露加 `--advertise-copy`。
* **源分辨率以上的档位自动隐藏**。1080p 源只给 360p/480p/720p/1080p，换 4K 源跑 2160p 自动出现。
  理由是放大不会变清楚，只会多花几倍流量和 CPU（实测 1080p 源做 4K 档：6s 一片要 **3154ms**、
  **8.12 Mbps**）。想强行放大加 `--allow-upscale`，或 `--max-height 1440` 换上限。
* **1080p 档和 `original` 档在 1080p 源上是一对好对照**：都是 1920x1080，一个 VBV 卡 5000k
  上限、一个直接 copy 源码率（实测这个源是 1569 kbps）。

### 这一轮做完的事

上上轮对上了 readme 里列的三条：

1. ✅ **预生成后几秒的切片** —— 请求第 i 片时，后台线程池顺手把后面 `--prefetch-ahead`（默认 18s）
   的切片转好；请求播放列表时预热第 0 片，点开就能播。
2. ✅ **最后一个切片，避免 0.0001 秒的空切片** —— 尾片不足 `--min-tail`（默认 1s）就并入前一片。
3. 继续研究与优化 —— 见下面「实测数据」里修掉的几个坑。

这一轮（多码率 + H.264 输出）：

1. ✅ **加了 1080p / 4K 档**，并且整个档位表改成按源分辨率生成（见上面「档位」）。
2. ✅ **`original` 档改成输出 H.264**：源是 H.264 就无损 copy，源是 AV1/HEVC 就转 H.264；
   另留 `original-copy` 保留「原编码原文件直通」。
3. 顺手做了一个不那么显然的东西：**`CODECS` 属性是量出来的，不是猜出来的**。
   见下面「实测数据」第 7 条 —— 手推这个值错了两次。

### 主要参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--segment-duration` | 6 | 单片时长（秒） |
| `--min-tail` | 1 | 尾片短于该值就并入前一片；`0` = 关掉（老行为） |
| `--prefetch-ahead` | 18 | 预生成后面多少秒；`0` = 回到纯按需基线 |
| `--prefetch-workers` | 按核数给 1~2 | 预取并发；CPU 吃紧的源给 1 更稳 |
| `--vbv-factor` | 1.0 | `-bufsize` 相对视频码率的倍数，见下面「VBV 超发」 |
| `--keyframe-mode` | first | `first`=只在片首打关键帧；`all`=all-intra（快但费流量） |
| `--preset` | veryfast | x264 preset，直接决定 TTFF：`ultrafast` 快 29%、SSIM 掉 0.013 |
| `--max-height` | 0（跟随源） | 档位高度上限，超出的档位不生成 |
| `--allow-upscale` | 关 | 允许源分辨率以上的档位（1080p 源也出 4K 档） |
| `--advertise-copy` | 关 | 把 `original-copy` 也列进 `master.m3u8` |
| `--warm-variants` | `original` | 启动预热哪些档位第 0 片，逗号分隔 / `all` / 空 = 不预热 |
| `--no-codec-probe` | 关 | 不编 1 帧量 `CODECS`，改成按分辨率估算（省启动时间、声明可能和实际不符） |
| `--no-warm` | 关 | 等价于完全不预热 |
| `--cache-dir` | `cache/` | 缓存目录。**跑两个实例做对照实验必须分开**，否则会抢同一个 `.part` |

### 观测接口

| 接口 | 用途 |
|---|---|
| `GET /stats` | JSON：请求数、命中/现转/等待、预取命中率、TTFF、p50/p95、各档位缓存进度 |

## 实测数据

环境：Windows / Python 3.12 / ffmpeg 8.1.2 / Ryzen 9 8940HX（16C32T）；
客户端是 `tools/bench.py`，复用一条 keep-alive 连接，模拟「10 秒缓冲水位」的播放器。
原始结果都在 [`bench/`](bench) 目录（每次运行的 JSON）。

### 1. 尾片：0.016 秒的“空气切片”

`sample-medium [h264 1920x1080 10m0s]` 真实时长 **600.016083s**。按 `ceil(600.016/6)` 切：

| | 片数 | 最后 3 个 EXTINF | 合计 |
|---|---|---|---|
| 老行为 | **101** | 6.000 / 6.000 / **0.016** | 600.016s |
| 现在 | **100** | 6.000 / 6.000 / **6.016** | 600.016s |

那一片不是免费的：实测请求它要 **303ms**（一次完整的 ffmpeg 进程 + HTTP 往返），
只换来 **1316 字节 / 0.016 秒**的内容。AV1 那个 23 分钟的源同理：237 片 → 236 片。

代价：合并后尾片 6.016s 比片长上限大，所以 `EXT-X-TARGETDURATION` 从 6 变成 **7**
（规范要求 target ≥ 每片时长，不能糊弄）。想让 target 保持 6，就得把尾巴摊到最后两片上，
但那样切片起点会离开 6s 网格，`-c copy` 档位也做不了 —— 留给以后试。

`python server.py --selftest` 会检查 4 个源 × 3 个档位：无空片、时间轴连续、
`EXTINF` 之和 == 真实时长、copy 档每个切片起点都落在真实关键帧上。当前全部通过。

### 2. `-force_key_frames "expr:gte(t,0)"` 是个大坑

原代码想表达「强制第一帧为关键帧」，但 `gte(t,0)` 对**每一帧**都成立 —— 等于把每片都编成
all-intra。实测 144 帧的片 = **144 个关键帧**（正确写法是 1 个）。

拿 ffv1 无损参考算 SSIM 对照（6~12s 那片，3 次重复）：

| 关键帧模式 | bufsize | 字节 | 关键帧数 | 平均 SSIM | 墙钟 |
|---|---|---|---|---|---|
| `expr:gte(t,0)` | 1250k | 1 885 828 | **144** | 0.927578 | 627ms |
| `expr:gte(t,0)` | 2500k | 2 066 308 | **144** | 0.928570 | 622ms |
| `expr:gte(t,n_forced*6)` | 1250k | 1 732 796 | **1** | 0.927201 | 730ms |
| `expr:gte(t,n_forced*6)` | 2500k | 1 948 056 | **1** | 0.928525 | 743ms |

* 同样码率上限下，all-intra **多花 6~9% 字节，SSIM 一点没赚**（差 ≤0.0005，5000k 那组甚至更低）。
* 但它**编码快约 16%**（620ms vs 740ms）—— 而首帧时间就是这个项目的核心指标，所以这不是纯粹的错，
  是一个真实的取舍。于是留成开关：默认 `--keyframe-mode first`（省流量），
  延迟优先的场景可以切 `all`。

端到端（960x400 源 → 360p，冷启动，无预取）：`first` TTFF 889ms / 2.325 Mbps，
`all` TTFF 680ms / 2.641 Mbps。
（这是 `720p` 档位还在、那个源还能出 720p 时的数字；现在 960x400 源只生成 `original` 和 `360p`，
档位表按源分辨率过滤了。结论不变：`first` 省字节、`all` 快。）

### 3. VBV 超发：每片都是新进程，每个进程的 VBV 都是满的

片子短、每片一个 ffmpeg 进程，于是每片开头都会“超发”比特，而 6 秒太短拉不回平均值。
`-bufsize` 才是这个现象的主开关（标称 2500k）：

| bufsize | 实测平均码率 | 相对标称 |
|---|---|---|
| 1250k | 2.31 Mbps | −7.6% |
| 2500k | 2.60 Mbps | +3.9% |
| 5000k（老代码 = 2×码率） | 2.96 Mbps | **+18.5%** |

老代码用 2× 码率当缓冲，实际码率打到 3.0 Mbps，而 master.m3u8 里只声明了 3.0 Mbps 的
BANDWIDTH（还含音频）—— 播放器的带宽预算是按声明值算的，等于被骗。
现在 `--vbv-factor 1.0`，BANDWIDTH 也改成 `(视频码率 + 音频码率) × 1.15` 估算。
同一条片子端到端：**老版本 2.833 Mbps → 现在 2.325 Mbps（−18%）**。

### 4. 关键帧扫描：改用 packet

`original` 档要按真实关键帧切，得先扫全片关键帧。老写法
`-skip_frame nokey -show_entries frame=pts_time` 要解析到帧层；改成
`-show_entries packet=pts_time,flags` 只看包（关键帧标志在包上就有）：

| 源 | frame 方式 | packet 方式 |
|---|---|---|
| 1080p 10 分钟 | 3189ms | **330ms** |

关键帧数量完全一致（156 个），启动少等 3 秒。

### 5. 预生成到底值多少

轻量源（960x400 → 720p，8 片，模拟 10s 缓冲的播放器）：

| 场景 | TTFF | 播放中 p50 | p95 |
|---|---|---|---|
| 纯按需（无预取、无预热）冷启动 | 1029ms | **1049ms** | 1119ms |
| 预取开 · 冷启动 | 930ms | **5.9ms** | 2062ms |
| 预取开 · 热缓存 | 6.9ms | 4.6ms | 5.2ms |
| 启动预热跑完后再打开 | **6.0ms** | 20ms | 1723ms |

播放过程中每一次切片请求：**1049ms → 5.9ms（约 180×）**。首片该转还是得转（TTFF 不变），
但后面每一片都已经躺在缓存里了。启动预热让「打开网页就能播」变成 6ms。

重负载源（AV1 1080p → 720p，单片转码 2.5s，8 片）：

| 预取 worker | TTFF | p50 | max | 单片平均转码 | 走完 8 片 |
|---|---|---|---|---|---|
| 0（关） | 1787ms | 2582ms | 3565ms | 2568ms | 35.8s |
| 1 | 1723ms | 166ms | 2798ms | 2691ms | 33.7s |
| 2 | 1733ms | **4.6ms** | 3367ms | **3374ms** | 33.7s |

**这里有个反直觉的结果**：2 个 worker 时单片平均转码从 2568ms 涨到 3374ms（+31%），
最坏延迟也更差 —— 请求路径 + 2 个预取 = 3 个 x264 并发，把 CPU 抢光了（这个源还要软解 AV1）。
预取不生产 CPU，它只是把 CPU 从「用户正在等的那一片」挪到「后面某一片」。
所以：**只有转码明显快于播放时，预取才是白赚的**；CPU 打满时加 worker 反而更糟。
默认值因此改成按核数给 1~2 个。

### 6. 编码参数前沿（同一个 6s 片，标称 2500k）

| 配置 | 墙钟 | 字节 | SSIM |
|---|---|---|---|
| veryfast（默认） | 889ms | 1 948KB | 0.9285 |
| veryfast + all-intra | ~740ms | 2 060KB | 0.9286 |
| veryfast + `-tune zerolatency` | 966ms | 2 159KB | — |
| ultrafast | **629ms** | 1 873KB | 0.9154 |

* `-tune zerolatency` 在短切片上是**反优化**：更慢、更胖。
* `ultrafast` 便宜 29% 的编码时间，代价是 SSIM 掉 0.013。
* 注意这个源的 SSIM 被「960x400 放大到 720p」这一步主导，编码器之间的差异被掩盖了
  （CRF18 无上限 = 4.98 Mbps 也只有 0.9327）。换原生 720p 以上的源，码率/质量差异会比这里明显。

### 7. 新档位的实测代价（1080p 源，6s 一片，veryfast）

| 档位 | 转码一片 | 一片大小 | 实际码率 | 声明 BANDWIDTH |
|---|---|---|---|---|
| `original`（copy） | **~93ms** | 871KB | 1.14 Mbps（= 源码率） | 1 954 651 |
| `360p` | 602ms | 624KB | 0.85 Mbps | 1 030 399 |
| `480p` | 663ms | 977KB | 1.33 Mbps | 1 720 399 |
| `720p` | 867ms | 1537KB | 2.07 Mbps | 3 022 200 |
| `1080p` | 1237ms | 2469KB | 3.35 Mbps | 5 933 999 |
| `2160p`（放大） | **3154ms** | 5943KB | 8.06 Mbps | 14 020 800 |

* 到 1080p 为止，单片转码都还在 6s 以内，预取跟得上；**4K 档基本跟不上了**
  （3154ms 编一片、播放 6s，只剩不到 2 倍余量，随便抢一下 CPU 就欠债），
  所以默认干脆不生成 4K 档，除非源本身是 4K。
* `original` 档是这个架构里最理想的一档：copy 一片 93ms，播放 6s，**65 倍余量**，
  预取随便排都不会欠债。1080p 重编档只有 4.8 倍余量。
* BANDWIDTH 的算法是 `(视频码率 + 音频码率) × 1.15`，AVERAGE-BANDWIDTH 再 ×0.85。

### 8. `CODECS` 属性是量出来的，手推错了两次

`CODECS` 不是装饰，播放器真的会拿它判断「这个档位我能不能解」。它的形状是
`avc1.PPCCLL`，其中 `PPCC` = `profile_idc` + `constraint_set_flags` —— **这个字节推不出来**：

| 输入 | 实际 SPS 里的 PPCC |
|---|---|
| `x264 -profile:v main` | `4d 40`（constraint_set1_flag=1） |
| 源是 High profile（copy 出来的） | `64 00` |
| 源是 Constrained Baseline | `42 c0` |

我先按「Main 就是 `4d40`」手推，结果 `original` 档在源是 H.264 时是 **copy** 的，
流里是源自己的 High profile，master 里却声明成 Main —— 声明与实际不符。
改成「按分辨率推 level、按 profile 名推 profile_idc」之后对了 profile，但 constraint 字节还是错的。

最后的做法是**编 1 帧，从 SPS 里读这三个字节**：

* 重编档：把命令行的 `-i <源>` 换成 `-f lavfi -i testsrc`（尺寸必须和源一样，
  否则 libx264 会按测试图案的尺寸定 level —— 用 64x64 试过一次，4K 档声明成了 level 1.0），
  只编 1 帧，`-f h264` 输出到 stdout 读 SPS。
* 直通档：**不能编测试图案**（输出的是源自己的字节），老老实实 copy 一片真源读 SPS。
* 全部档位加起来约 0.5s 启动开销，`--no-codec-probe` 可以关掉换成估算。

`tools/check_codec.py` 会把这个声明和**真实切片**里的 SPS 逐档位对一遍（4 个源全过）。
`tools/smoke.py` 更进一步：它下载真实的 `seg0.ts`，从返回的字节里读 SPS 和声明比对 ——
这才是播放器真正会看到的东西。

## 踩到的坑（都被基准测试逼出来的）

* **自锁死**：`segment_plan()` 持着非重入的 `_CACHE_LOCK` 又去调 `_keyframe_times()`（它也要这把锁），
  启动直接卡死、一行日志都不打。现在算方案时不持锁。
* **两个实例共用一个缓存目录**：会互相抢同一个 `segN.ts.part`，`os.replace` 报
  `WinError 32 另一个程序正在使用此文件`。现在 `os.replace` 带退避重试，
  且只要正式文件已经完整就算这活干完了；另外加了 `--cache-dir`。
* **预取撞上请求**：请求路径没命中就排队等锁（不重复转），预取路径抢不到锁直接放弃。
  等锁的请求会记为 `waited`，面板上能看见。
  **这条有个副作用我没解决**：请求播放列表时会把第 0 片丢给预取 worker 预热，
  紧接着客户端就来要第 0 片 —— 于是客户端只能等那个 worker 把整片转完
  （实测 360p 冷启动：TTFF 336ms，其中 335ms 都在等这把锁；客户端自己转也是 335ms）。
  墙钟时间一样，但白烧了「本该能剪掉」的一次转码。想彻底解决得让 worker 发现
  「有人在等这片」就让路，或者让请求路径能抢占，属于调度器改造。
* **探测命令行被自己改坏过两次**：`measure_h264_codec_string()` 是拿真实的 ffmpeg 命令行
  改出来的，改错了不会报错、只会静默退回估算值，表现成「CODECS 差了半个字节」。
  两个具体的坑：把输入侧的 `-f lavfi` 和输出侧的 `-f mpegts` 一起删掉了；
  以及用 `rest.pop()` 删输出路径 —— 命令行最后一个参数其实是 `-muxpreload 0` 的 `0`，
  pop 掉它就得到 `Expected number for muxpreload but found: -frames:v`。
  现在输出路径按字符串匹配删，并且有 `tools/check_codec.py` 逐档位核对。
* 基准脚本自己也有 bug：最初的卡顿判据把“等缓冲”的睡眠算进了到达时间，会虚报卡顿。
  现在按播放器缓冲水位做事件推进（下载和等待期间都以 1× 消费缓冲），并额外报「最低缓冲水位」。

## 已知限制 / 下一步

* 尾片合并会让 `EXT-X-TARGETDURATION` 变大 1（见上）。可以把尾巴摊到最后两片上避免，但要放弃网格对齐。
* **4K 档很勉强**：1080p 源放大到 4K，6s 一片要 3154ms（只剩 1.9 倍余量），
  预取基本跟不上；而且 H.264 在 4K 上性价比很差。真 4K 要么源本身就是 4K，
  要么加 HEVC/AV1 档位（`-c:v libx265` / `libsvtav1`），别用 H.264。
* `original` 档在源是 AV1/HEVC 时用 `crf 18` **不控码率**：这一档的定位是「源画质 + H.264 兼容性」，
  压到某个上限就违背初衷；要严格控码率用固定档位。副作用是 CRF 档的单片大小不可预测，
  BANDWIDTH 只能按源码率 ×1.3 估。
* `original-copy` 档只能单独打地址用：AV1/HEVC 装进 MPEG-TS 不符合 HLS 规范
  （AV1 在 HLS 里应该走 fMP4），浏览器播放器基本都解不了。ffmpeg 本身能转出来。
  `--advertise-copy` 会把它列进 master，但播放器多半还是放不了。
* 预取自适应：目前 worker 数是静态的。可以按「最近单片转码耗时 / 片长」动态调节，
  转码接近实时就干脆不预取 —— 上面第 5 节的数据说明这才是正确策略。
* 缓存没有上限：一部片子播完，所有档位的切片都会留在磁盘上。真实项目要加 LRU + 容量上限。
  档位变多以后这个问题更明显（现在是原来 3 倍左右的档位数）。
* 批量预取：现在每片一个 ffmpeg 进程。预取连续几片时其实可以一个进程 + `-f segment` 连出几片，
  省掉重复的 seek 和解码。这个实验还没做。4K/1080p 档最需要这个优化。
* `/stats` 的 TTFF 是**服务端**口径（master.m3u8 请求 → 第一个切片响应），
  不含播放器解封装/解码/渲染，当代理指标看。

## 对照实验怎么做

老版本（改之前）本身就是一个很好的对照。把它拉到一个 git worktree 里，
用 junction 共用媒体文件、分开缓存目录，两个实例同时跑：

```bash
git worktree add --no-checkout ../hls-test-baseline HEAD
cd ../hls-test-baseline && git checkout HEAD -- server.py readme.md tools
# Windows: mklink /J media ..\hls-test\media   （Linux/mac: ln -s）
python server.py --port 8090            # 老版本
python tools/bench.py --url http://127.0.0.1:8090 --label baseline
```

同一把尺子下的冷启动对比（960x400 → 720p）：
